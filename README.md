# תוקף | בדיקת הפניות במכרז לפני פרסום

## הבעיה

עורכי מכרזים וצוותי רכש נעזרים בסעיפים ממכרזים קודמים. מספר הוראת תכ״ם יכול להישאר בסעיף גם אחרי שפורסמה מהדורה חדשה, ולעיתים משתנה גם הקשר בין המספר לכותרת. בדיקה ידנית מחייבת לאתר כל הפניה, למצוא את היסטוריית המהדורות ולברר מה חל ביום הפרסום. הפניה מיושנת עלולה להשאיר את המציעים עם דרישות לא ברורות.

## הפתרון

העורכת מעלה טיוטת Word, בוחרת מועד פרסום ויכולה להוסיף מועד בדיקה קודמת. לכל הפניה שזוהתה מוצגים הציטוט, המיקום במסמך, תוצאת הבדיקה וקישור למקור או לחיפוש בתכ״ם. העורכת יכולה לחזור לסעיף ולהחליט אם לתקן אותו.

- כשמצוינים מהדורה או תאריך תחילת תוקף, המערכת משווה אותם למהדורה שחלה ביום הפרסום.
- כשמופיע רק מספר הוראה, המערכת מציגה לידיעה את המהדורה שחלה באותו יום. אם הוזן גם מועד בדיקה קודמת, היא בודקת אם המהדורה השתנתה בין התאריכים.
- כאשר חסרה היסטוריית מהדורות או שיש חפיפה בין תקופות תוקף, הדוח מסביר מדוע נדרש אימות ידני.

לדוגמה, סעיף 5.3 במכרז אשל הנשיא מפנה להוראה 1.4.3 ומציין את התאריך 09.05.2021. ביום פרסום המכרז, 21.08.2025, כבר חלה מהדורה 6. הסעיף מפנה גם לנוסח התקף מעת לעת, ולכן הדוח מסמן **נדרשת בדיקה** ומציג לעורכת את התאריך שדורש עיון. [חוברת המכרז, עמ׳ 8](https://mr.gov.il/ilgstorefront/he/p/attachment/005056BF4F1A1FE09FCEACB1AAC892EE/%D7%97%D7%95%D7%91%D7%A8%D7%AA%20%D7%94%D7%9E%D7%9B%D7%A8%D7%96#page=8) · [כרטיס ההוראה](https://takam.mof.gov.il/document/H.1.4.3)

## הרצה מקומית

נבדק עם Node.js 20.17.0 ו־npm 10.8.2. חלצו את כל תוכן ה־ZIP, פתחו מסוף בתיקייה שבה נמצא `package.json` והריצו משם את שתי הפקודות.

```sh
npm ci
npm run dev
```

פתחו בדפדפן את [האתר המקומי](http://127.0.0.1:4173). פקודת ההפעלה בודקת טיפוסים, בונה את ממשק React ומפעילה שרת אחד שמגיש את הממשק ואת ה־API. לעצירה לחצו Ctrl+C במסוף. ההתקנה הראשונה דורשת גישה ל־npm. לבדיקת תוקף מול תכ״ם נדרש חיבור לאינטרנט. קובץ ה־Word מעובד בשרת המקומי. הפניות החוצה מיועדות לקטלוג הציבורי ולמזהי ההוראות. כשאין חיבור, אפשר לבדוק לפי הגיבוי המקומי, המכסה את הוראות 1.4.2 ו־1.4.3 בלבד.

```sh
npm test
```

להפעלה עם נכסים שכבר נבנו אפשר להריץ `npm start`. ההגדרות ב־`.env.example` מציגות את ברירות המחדל. לשינוי ההגדרות העתיקו אותו ל־`.env` וערכו את `HOST` (כתובת ההאזנה), `PORT` (ברירת המחדל 4173) או `CATALOG_PATH` (נתיב הגיבוי המקומי). הקובץ `.env` מוחרג מ־Git. החיבור ל־API הציבורי פועל ללא מפתחות גישה. השרת מקבל קובצי DOCX עד 10 MiB ומעבד אותם בזיכרון.

## בדיקה ראשונה בדפדפן

1. לחצו על **טעינת טיוטה לדוגמה**. ייבחרו הקובץ eshel-demo.docx ותאריך הפרסום 21.08.2025. אפשר גם לבחור את הקובץ ידנית מתוך examples.
2. לחצו על **בדיקת ההפניות**. בדוח יופיעו חמישה מופעים. בראשו יופיע סעיף 5.3 עם התאריך מהטיוטה, מהדורה 6 ותאריך תחילתה 19.09.2024. פתחו את **הצגת המקום בטיוטה** ואת **כרטיס ההוראה הרשמי** כדי לבדוק את הממצא מול שני המקורות.
3. שנו את מועד הפרסום ל־25.01.2024 והריצו שוב. בסעיף 5.3 תופיע התאמה למהדורה 5. כדי לראות שינוי גם בהפניה שכוללת מספר בלבד, בדקו פרסום ב־21.08.2025 ובדיקה קודמת ב־18.09.2024.
4. לבדיקה על מכרז Word ממשלתי מקורי העלו את fuel-tender-07-2021.docx ובחרו 02.02.2022. בפסקה המתחילה במילים ״בכל שלושת הסלים״ יופיעו הוראה 1.4.3 ומהדורה 5. אפשר לנסות גם את מכרז הלמ״ס המקורי או את קובץ ההדגמה ללא הפניות.

לתרחיש קצר עם התראה אחת ושלוש הפניות תואמות, העלו את [טיוטת הבדיקה](examples/eshel-check-one-expired.docx) ובחרו 21.08.2025.

סרטון ההדגמה מציג את הסעיף המקורי, ההעלאה, ההכרעה בשני תאריכים ופתיחת הכרטיס הממשלתי. [צפייה בסרטון](demo.mp4)

## התכנון הטכני

יישום אחד ב־TypeScript משרת את ממשק React ואת ה־API מאותה כתובת. הלקוח שולח קובץ ותאריכים לשרת Node.js. השרת מחלץ את הטקסט, מזהה הפניות, מבקש מתכ״ם היסטוריה עבור ההוראות הרלוונטיות ומחזיר דוח JSON לתצוגה. הטיוטה נשארת בזיכרון השרת במשך העיבוד. לתכ״ם נשלחות בקשות לקטלוג ולמזהי ההוראות בלבד.

| רכיב | אחריות |
|---|---|
| `client/` | מסך React בעברית, בחירת קובץ ותאריכים, דוח עם ציטוטים וקישורי מקור |
| server/http.ts | הגשת הממשק וקבלת העלאות multipart בנתיב POST /api/review עם השדות file, publication ו־previous האופציונלי |
| `server/word.ts` | פתיחת ארכיון ה־DOCX באמצעות `yauzl`, פענוח XML באמצעות `@xmldom/xmldom` וקריאת גוף ה־DOCX לפי סדר המסמך, חיבור קטעי טקסט שפוצלו בעיצוב ושמירת מיקום בפסקה או בטבלה |
| server/review.ts | זיהוי הפניות לפי הקשר והשוואת מהדורות לפי תאריכי תוקף |
| server/takam.ts | טעינת קטלוג ההוראות של תכ״ם ושליפת היסטוריית המהדורות לפי ההפניות במסמך |
| data/historical-references.json | מקורות רשמיים המתעדים צירופים היסטוריים של מספר וכותרת |
| data/catalog.json | גיבוי מקומי מתוארך של שתי הוראות ושבע מהדורות |
| מקורות רשמיים | מהדורות Word, חוברת אשל הנשיא ב־PDF ותשובות JSON מה־API |
| examples, tests | מכרזים מקוריים, טיוטות הדגמה, סימון ידני, בדיקות כללים ובדיקות העלאה לשרת |

בכל בדיקה השרת משתמש בקטלוג הציבורי של תכ״ם ושולף את היסטוריית המהדורות של ההוראות שזוהו. הקטלוג נשמר בזיכרון עד חמש דקות. תאריך ההתחלה ותאריך הסיום נכללים בטווח התוקף, והבדיקה מדווחת על טווחים חופפים או חסרים. כשהכותרת ליד המספר מתאימה להוראה אחרת, הדוח מציין את הפער ומקשר לכרטיס המתאים לכותרת. הגיבוי המקומי משמש בעת כשל גישה ומוצג כגיבוי בדוח. במקרה של מספר ששימש למסמך אחר בעבר, המערכת יכולה לזהות את ההפניה לפי המספר, הכותרת ומועד הפרסום, אם השימוש מתועד במקורות רשמיים. התוצאה מציגה את המקורות ואת העובדה שזיהוי המסמך עדיין אינו אימות מהדורה. טווח התיעוד בקובץ משמש לבחירת ראיות רלוונטיות ואינו טווח תוקף. [קטלוג ההוראות](https://takam.mof.gov.il/api/Document) · [מקורות הנתונים והמסמכים](examples/SOURCES.md)

הקורא מעבד את הפסקאות ואת תאי הטבלאות בגוף המסמך. הוא שומר ציטוט מקור ומזהה מספר סעיף הכתוב בטקסט. כשמספור Word מחושב אוטומטית ואינו חלק מהטקסט הוא מציג מיקום בפסקה או בטבלה. כותרות עליונות ותחתונות, הערות שוליים וטקסט בתמונות חורגים מהכיסוי. זיהוי ההפניות מבוסס על תבניות עבריות מפורשות. הסריקה אינה מבצעת OCR, השוואה משפטית של נוסחים או עריכה של קובץ Word.

## בדיקות ותוצאות

חבילת הבדיקות כוללת 17 בדיקות באמצעות `node:test`. בדיקות החיבור לתכ״ם משתמשות בתשובות API מבוקרות כדי לשחזר גם השבתה של המקור. בדיקות ההעלאה משתמשות במדגם מקומי קבוע כדי לשחזר תוצאות ללא תלות באתר תכ״ם. לפני ההרצה סומנו המופעים, המיקומים והתוצאות הצפויות. בדיקות האינטגרציה מעלות קבצים אמיתיים לשרת HTTP זמני, משוות כל ממצא לסימון ובודקות גם תוצאות עודפות בתוך תחום הסימון. גיבובי SHA-256 מזהים את שני קובצי המכרז המקוריים. [טבלת הציפיות](examples/expected.json)

| מסמך ותחום הסימון | סומנו | נמצאו | הוחמצו | זוהו בטעות |
|---|---:|---:|---:|---:|
| טיוטת אשל הנשיא, כל מופעי ההדגמה | 5 | 5 | 0 | 0 |
| מכרז הלמ״ס המקורי, ההפניות הממוספרות בגוף החוברת | 4 | 4 | 0 | 0 |
| מכרז הדלק המקורי, הפניות לשתי ההוראות שבמדגם | 1 | 1 | 0 | 0 |
| הוראה 1.4.3 המקורית, הפניות ל־1.4.2 | 3 | 3 | 0 | 0 |
| תמלול סעיף 5.2 מאשל הנשיא, קובץ ללא הפניות | 0 | 0 | 0 | 0 |

סעיף 5.3 בהדגמה תומלל מחוברת PDF. הסעיפים הנוספים והטבלה מסומנים בקובץ כתרחישי בדיקה. מכרז הדלק ומכרז הלמ״ס צורפו כקובצי Word שפרסם מינהל הרכש. התוצאות בטבלה מתייחסות רק לתחומי הסימון המפורטים בה.

הבדיקות מכסות גם את יום סיום מהדורה ואת היום שאחריו, טווחים חופפים, תאריך מחוץ לכיסוי, תאריך שאינו תאריך מהדורה, השוואה לבדיקה קודמת, הפניה פנימית, שם ללא מספר, קובץ פגום וקלט תאריכים שגוי. אותה העלאה נבדקת פעמיים כדי לוודא שהתוצאה חוזרת על עצמה.

## החלטות הנדסיות ואיכות

**מדוע כללים מפורשים?** לכל התראה צריך להיות הסבר שהעורכת יכולה לבדוק מול הטיוטה והמקור. לכן חילוץ הטקסט, זיהוי ההפניה ובחירת המהדורה לפי תאריך הם שלבים נפרדים. אפשר לבדוק כל כלל עם קובץ אמיתי, כולל צורות כתיב כמו תכ״ם ותכ״מ. ההחלטה אם לשנות סעיף משפטי נשארת בידי העורכת.

**מה נשאר מחוץ לגרסה הראשונה?** המימוש מתמקד ב־DOCX. הרחבה שימושית תהיה קורא PDF שיחלץ טקסט ומספרי עמודים ויעביר אותם למנוע הבדיקה הקיים. בשלב ראשון כדאי לבדוק קובצי PDF המכילים טקסט עברי, כולל סדר הקריאה בטבלאות. מסמכים סרוקים ידרשו גם OCR ובדיקה של דיוק הספרות במספרי ההוראות.

**מה הייתי משנה לקראת שימוש רחב?** הייתי מעביר את איסוף נתוני תכ״ם לתהליך סנכרון מתוזמן ששומר היסטוריית מהדורות, קישור מקור ומועד איסוף במסד נתונים משותף. כך כמה שרתים יוכלו לבדוק מכרזים במקביל על בסיס אותם נתונים, ואפשר יהיה לשחזר דוח לפי תמונת הנתונים ששימשה אותו. המחיר הוא פער זמן בין עדכון בתכ״ם לסנכרון הבא, ולכן חשוב להציג ולנטר את מועד הסנכרון האחרון שהצליח.

## פריסה ותפעול בסביבה ארגונית

1. **בנייה וקידום אוטומטיים.** בכל שינוי, תהליך CI יריץ `npm ci`, אחריו `npm test` ו־`npm run build`. הוא יארוז בגרסת קונטיינר מזוהה את השרת ותלויות ההרצה, `client/index.html`, תוצרי `dist/`, קובצי `data/` וטיוטת ההדגמה. אותה גרסה תקודם מסביבת בדיקות לייצור ותופעל באמצעות `npm start`. כתובת ההאזנה בקונטיינר (`HOST=0.0.0.0`), הפורט ונתיב הגיבוי יוגדרו בסביבה. הגישה לאתר תעבור דרך שער ארגוני עם HTTPS והזדהות.
2. **אימות הפריסה.** בדיקת עשן תוודא שעמוד הבית והנכסים נטענים וש־`GET /api/catalog` מחזיר מידע על המדגם. כדי לבדוק גם את החיבור החי, היא תעלה את `eshel-demo.docx` ל־`POST /api/review` עם תאריך 21.08.2025 ותוודא שחזרו חמישה ממצאים, שבסעיף 5.3 זוהתה מהדורה 6 ושמקורה הוא תכ״ם. תשובת HTTP מוצלחת לבדה יכולה להתקבל גם כשהשרת משתמש בגיבוי.
3. **זיהוי כשל והתאוששות.** אם תכ״ם ישנה את שדה תאריך תחילת התוקף, בקשת המקור עשויה להחזיר HTTP 200 עם רשומה שהשרת אינו יכול לקרוא. כיום השרת משתמש בגיבוי להוראות המכוסות בו ומסמן חוסר בנתונים עבור יתר ההוראות. בפריסה ארגונית הייתי מוסיף מדדים לכשלי קריאת מהדורות ולשיעור הדוחות שהשתמשו בגיבוי, ומתריע על עלייה מתמשכת בלי לרשום תוכן מכרזים. אם הכשל הופיע בעקבות גרסת יישום חדשה, חוזרים לגרסה האחרונה שעברה את בדיקת העשן. אם השתנה מבנה הנתונים במקור, מעדכנים את רכיב החיבור, מוסיפים בדיקה עם התגובה שהשתנתה ומאמתים שוב מול המקור לפני קידום הגרסה.
